## 1. 项目概述

### 1.1 项目背景

本项目结合作者在 Unreal Engine 5 与 Blender 方向的独立游戏开发经验自选。在游戏开发过程中，美术资产（模型、贴图、蓝图、音效、动画等）数量庞大、版本迭代频繁，同时存在跨角色（负责人、美术、程序、策划、外部协作者）协作的需求。传统方式下，资产散落在网盘与聊天记录中，缺少版本追溯、审核流转与进度可视化的统一入口。

### 1.2 项目目标

构建一个面向游戏项目的**资产管理与团队协作**平台，覆盖：

- **项目与成员管理**：多项目管理、邀请制加入、角色权限（RBAC）。
- **美术资产与版本管理**：资产分类、版本历史、状态审核流转、大文件分片上传与秒传。
- **任务看板与协作**：四列看板拖拽、任务评论与 @提及、站内通知。
- **统计与进度可视化**：资产完成率、燃尽图、成员工作量、周报/月报、导出。

### 1.3 交付范围

项目按四个模块迭代交付：模块 1（项目与成员）→ 模块 2（美术资产）→ 模块 3（任务看板）→ 模块 4（统计可视化）。当前四个模块均已实现，前后端打通，附有完整的单元测试与端到端验证脚本。

## 2. 需求分析

### 2.1 用户角色

| 角色 | 定位 | 说明 |
|---|---|---|
| OWNER（负责人） | 项目创建者 | 项目内全权限：项目设置、成员管理、资产审核、看板、统计 |
| ARTIST（美术） | 资产生产者 | 资产读写、删除草稿、看板读写、可看统计；**无审核权** |
| PROGRAMMER（程序） | 程序开发 | 资产只读、看板读写、可看统计 |
| DESIGNER（策划） | 策划 | 资产只读、看板读写、可看统计 |
| VIEWER（外部协作者） | 外部协作 | 项目/资产/看板只读，**无统计、无任何写权限** |

> 另有系统级 `ADMIN / MEMBER` 用户角色（`sys_user.role`），与项目内角色（`project_member.role`）是两个独立维度。

### 2.2 功能需求（按模块）

**模块 1：项目与成员管理**
- 注册 / 登录 / 登出 / 当前用户信息
- 项目 CRUD 与状态流转（ACTIVE / PAUSED / ARCHIVED）
- 邀请码加入、成员角色调整、成员移除、唯一负责人保护

**模块 2：美术资产与版本管理**
- 二级分类树管理
- 资产 CRUD（逻辑删除）、资产编号自动生成、分页筛选
- 版本上传 / 下载 / 回滚 / 对比、大文件分片上传与秒传
- 状态审核流转（IN_PROGRESS → PENDING → APPROVED / REJECTED / DEPRECATED）

**模块 3：任务看板与协作**
- 四列看板（TODO / DOING / REVIEW / DONE）、拖拽落位（服务端为准）
- 任务 CRUD、指派、关联资产、乐观锁并发控制
- 任务评论与 @提及、站内通知与未读角标轮询

**模块 4：统计与进度可视化**
- 资产完成率 / 分类分布 / 燃尽图 / 任务趋势 / 成员工作量
- 周报 / 月报（生成即落快照）
- 统计报表 Excel 导出

## 4. 功能模块设计

### 4.1 模块 1：项目与成员管理

- **认证**：注册 / 登录（JWT 签发，`expire-minutes=480`）/ 登出（jti 写入 Redis 黑名单）/ `me`（当前用户 + 参与项目）。
- **项目**：创建即自动成为 OWNER；`GET /api/projects` 只返回 `ACTIVE` 成员关系。
- **成员**：邀请（生成一次性邀请码）→ 凭码加入 → 码立即作废；角色调整与移除；**唯一 OWNER 保护**（不能移除/降级最后一名负责人）。

### 4.2 模块 2：美术资产与版本管理

- **分类**：二级分类树；`code` 作为资产编号前缀；删除前校验「无资产且无子分类」。
- **资产**：`asset_no` 由 `AssetNoGenerator`（Redis INCR）+ 项目分类前缀生成，唯一不复用；逻辑删除保留历史。
- **版本**：版本只增不改，`is_current` 标记当前版本，支持回滚与两版本元数据对比。
- **状态流转**：白名单 `IN_PROGRESS → PENDING → APPROVED → DEPRECATED`，打回走 `REJECTED`；仅 OWNER/ARTIST 可提交审核，仅 OWNER 可审核。
- **大文件上传**：`check-md5`（秒传）→ `init`（分配 uploadId）→ `chunk`（乱序分片）→ `complete`（`ChunkMerger` 按序合并 + MD5 校验）。

### 4.3 模块 3：任务看板与协作

- **看板**：四列分组；`sort_order` 大间隔（+1000）实现拖拽落位取中值，一条 UPDATE 完成。
- **任务**：`version` 乐观锁，并发拖拽返回 409；`finished_at` 随拖入/拖出 DONE 写/清。
- **评论**：支持 @提及（`MentionParser` 解析）；任务负责人也会收到评论通知。
- **通知**：统一入口 `NotificationService.push()`，硬规则「不给自己发通知」；触发点覆盖指派、改列、评论/提及、审核、临近截止。

### 4.4 模块 4：统计与进度可视化

- 八个只读统计接口，**全部把 `pid` 放路径里**（避免越权依赖客户端可改写的 `X-Project-Id` 头）。
- **燃尽图**：理想线逐日线性递减；实际线按 `task_status_log` 逐日回放（与任务当前状态无关）。
- **工作量**：总体标准差口径（÷n），μ=0 时均衡度取 1.0，均衡度可为负不截断。
- **周报/月报**：四段结构 + `ReportRiskAdvisor` 自动风险提示；`project_report` 快照用 `INSERT ... ON DUPLICATE KEY UPDATE` 幂等 upsert。

## 5. 数据库设计

### 5.1 表清单（13 张）

| # | 表 | 模块 | 说明 |
|---|---|---|---|
| 1 | `sys_user` | 1 | 系统用户（`deleted` 逻辑删除） |
| 2 | `project` | 1 | 项目（`member_count` 冗余） |
| 3 | `project_member` | 1 | 项目成员（无 `deleted`，`status` 软删） |
| 4 | `asset_category` | 2 | 资产二级分类（无 `deleted`） |
| 5 | `asset` | 2 | 资产主表（逻辑删除） |
| 6 | `asset_version` | 2 | 资产版本（只增不删） |
| 7 | `asset_status_log` | 2 | 资产状态流转（只追加） |
| 8 | `task` | 3 | 任务（`version` 乐观锁） |
| 9 | `task_comment` | 3 | 任务评论 |
| 10 | `task_status_log` | 3 | 任务状态日志（只追加） |
| 11 | `notification` | 3 | 站内通知（只标记已读） |
| 12 | `project_report` | 4 | 报表快照（JSON 类型） |
| 13 | `calendar_dates` | 4 | 日期维表（无实体类/Mapper） |

### 5.2 实体关系（核心）

```
sys_user 1 ──── n project_member n ──── 1 project
project  1 ──── n asset_category n ──── 1 asset ──── n asset_version
   │                                          │
   │                                          └─── n asset_status_log
   ├──── 1 ──── n task ──── n task_comment
   │                │
   │                └─── n task_status_log
   ├──── 1 ──── n notification
   ├──── 1 ──── n project_report
   └──── 1 ──── n (task 关联 asset 为可空多对一)
```

### 5.3 关键设计决策

- **字符集统一 `utf8mb4`**：项目名、昵称常含 emoji，`utf8`（3 字节）存不下会报 `Incorrect string value`。
- **逻辑删除与状态位的取舍**：
  - `asset` / `task` / `task_comment` / `sys_user` 用 `deleted` 列（历史可追溯）。
  - `project_member` **刻意无 `deleted`**，用 `status=REMOVED` 状态位——`uk_project_user` 唯一约束下，逻辑删除后重新邀请会撞唯一键。
  - `asset_category` 无 `deleted`：删除前校验「无资产且无子分类」，不存在孤儿中间态。
  - `asset_version` / `task_status_log` / `asset_status_log` / `notification` 只增不删，保证追溯。
- **冗余 `project_id`**（`asset_version`、`task_comment`、`task_status_log`）：让「单资源查询必须带项目条件」这条硬约束不必先回查主表。
- **`member_count` 冗余列**：唯一维护入口 `refreshMemberCount`，口径 = 未移除成员数（含 INVITED）。
- **`sort_order` 大间隔**：每次 +1000，拖拽取相邻中值，间隔 < 10 才重排整列。
- **`project_report.snapshot_json` 用 JSON 类型**：快照结构随报表演进，历史快照保持原样，不必 ALTER TABLE。
- **`calendar_dates` 无实体/Mapper**：只被燃尽图手写 SQL `LEFT JOIN` 使用，是全局维表，天然无项目维度；建 Mapper 反而破坏「手写 SQL 必带 project_id」的契约。

### 5.4 关键索引与唯一约束

- `uk_project_user(project_id, user_id)`：防止重复成员。
- `uk_project_code(project_id, code)`、`uk_project_asset_no(project_id, asset_no)`：编号/编码项目内唯一。
- `uk_asset_version(asset_id, version_no)`：版本号自增的最后一道防线。
- `uk_project_period(project_id, report_type, period_start)`：报表幂等 upsert 的基础。
- `idx_user_read(user_id, is_read, create_time)`：同时覆盖「未读列表」与「未读数」两个查询。

## 6. 权限与安全设计

### 6.1 RBAC 权限矩阵

权限点定义在 `Permission` 枚举（10 个），角色→权限映射**只在 `RolePermissionMap` 一处定义**：

| 权限点 | OWNER | ARTIST | PROGRAMMER | DESIGNER | VIEWER |
|---|---|---|---|---|---|
| PROJECT_READ 查看项目 | ✅ | ✅ | ✅ | ✅ | ✅ |
| PROJECT_WRITE 修改项目 | ✅ | ❌ | ❌ | ❌ | ❌ |
| MEMBER_MANAGE 成员管理 | ✅ | ❌ | ❌ | ❌ | ❌ |
| ASSET_READ 查看资产 | ✅ | ✅ | ✅ | ✅ | ✅ |
| ASSET_WRITE 编辑资产 | ✅ | ✅ | ❌ | ❌ | ❌ |
| ASSET_REVIEW 资产审核 | ✅ | ❌ | ❌ | ❌ | ❌ |
| ASSET_DELETE 删除资产 | ✅ | ✅ | ❌ | ❌ | ❌ |
| TASK_READ 查看看板 | ✅ | ✅ | ✅ | ✅ | ✅ |
| TASK_WRITE 编辑任务 | ✅ | ✅ | ✅ | ✅ | ❌ |
| STAT_READ 查看统计 | ✅ | ✅ | ✅ | ✅ | ❌ |

### 6.2 鉴权链路（两层防护）

**第一层：`@ProjectPermission` + AOP 切面**
1. 校验登录态（`UserContext` 有 userId）。
2. `ProjectIdResolver` 解析 projectId（**路径变量优先、`X-Project-Id` 头兜底**）。
3. 查询 `project_member`，条件为 `project_id + user_id + status=ACTIVE` **三者缺一不可**。
4. `RolePermissionMap.allows(role, required)` 判定，不足抛 `BizException(403)`。
5. 通过后把 `projectId` / `projectRole` 写入 `UserContext`。

**第二层：SQL 强制携带 `project_id`**
所有单资源查询的条件都带 `project_id`，不依赖「按主键查出来再在 Java 里判断归属」。`MapperSqlContractTest` 用单元测试断言 SQL 片段含 `project_id` 且参数真值被绑定。

### 6.3 会话与令牌

- **JWT**：HS256，密钥 ≥ 32 字节（可环境变量注入），`sub` 存 userId，`jti` 用于登出。
- **登出黑名单**：`jti` 写 Redis 黑名单（TTL = 令牌剩余有效期），拦截器命中即拒绝。
- **ThreadLocal 隔离**：`UserContext` 在 `afterCompletion` 中 `clear()`，防止 Tomcat 线程复用导致串号。

### 6.4 其它安全点

- **越权返回真实 HTTP 403**：HTTP 状态码与业务码同值（400/401/403/404/409/500），便于 curl/Postman 直接判断。
- **逻辑删除**：删除操作不物理抹除数据。
- **文件存储**：本地路径可配置（`STORAGE_PATH`），预留 MinIO 抽象接口。

## 7. 关键设计决策与权衡

### 7.1 概览与统计缓存

| key 前缀 | 内容 | TTL | 失效时机 |
|---|---|---|---|
| 项目概览缓存 | `ProjectOverviewVO` | 10 分钟 | 项目/成员写操作 |
| `gah:stat:{pid}:asset-completion` | 资产完成率 | 10 分钟 | 任务/资产/成员写操作 |
| `gah:stat:{pid}:asset-category` | 分类分布 | 10 分钟 | 同上 |
| `gah:stat:{pid}:workload` | 成员工作量 | 10 分钟 | 同上 |

- **统计缓存失效挂载在 `ProjectOverviewCache#evict()` 通道上**：一次修改、一处失效，杜绝「概览对了、统计图还是旧的」半失效。
- **燃尽图与任务趋势刻意不缓存**：横轴含「今天」，缓存一天就会让曲线「数字看着对、就是不动」，极难排查。
- **不放任何用户维度字段进项目级缓存**：`myTasks` 等用户维度数据实时查库，避免串号。

### 7.2 乐观锁（任务拖拽）

- `task.version` 乐观锁，`move` 接口携带 version，冲突返回 409。
- **拖拽落位以服务端为准**：按相邻卡片 `sort_order` 算新位置，响应返回服务端计算的最终 `sortOrder`。

### 7.3 分片上传与秒传

- `check-md5` 命中已存在文件直接建版本（秒传），不重复传输。
- 分片乱序上传后 `ChunkMerger` 按序合并，合并后校验整包 MD5。
- `ChunkCleanupTask`（每天 3 点）清理超过 24 小时的残留分片。

### 7.4 存储抽象

`StorageService` 接口 + `LocalStorageService` / `MinioStorageService` 两实现，`gameasset.storage.type=local|minio` 切换。MinIO 目前为占位实现（方法体抛错），演示只用 `local`。

### 7.5 燃尽图口径修正

实际线 SQL 额外增加 `t.create_time < DATE_ADD(d.stat_date, INTERVAL 1 DAY)`，排除「在该日期之后才创建的任务」，修正文档原文的缺陷（一个 10 月才建的任务会被算进 9 月的剩余故事点）。

### 7.6 报表幂等 upsert

`project_report` 用 `INSERT ... ON DUPLICATE KEY UPDATE` 一条语句解决，**不采用**「`catch(DuplicateKeyException)` 后同一事务里重查」——后者在 MySQL REPEATABLE READ 下，快照读看不到并发事务刚提交的行，异常最终会冒到用户面前。

### 7.7 手写 SQL 契约

「所有手写 SQL 都必须带 `project_id`」是全局硬约束，`MapperSqlContractTest` 用否定式断言守住（例如燃尽图 SQL 里**不许出现** `column_status` 与 `finished_at`）。

## 8. 非功能需求

### 8.1 性能

- 概览与统计走 Redis 缓存，读路径低延迟。
- 分片上传支持 2GB 大文件（`max-file-size: 2GB`）。
- 未读角标走索引 `idx_user_read`，Redis 缓存 5 分钟。

### 8.2 可维护性

- **权限矩阵单点定义**，调整角色/权限只改一处。
- 分层清晰（controller / service / support / mapper / storage），支撑组件独立成类。
- 前后端均有完整注释，解释「为什么」而非「是什么」。
- 全套验证脚本（`.tools/*.ps1`）幂等可重复执行，路径随工程目录自动推导。

### 8.3 可移植性

- 便携工具链（`.tools`）随包携带 JDK / Maven / Node / MySQL / Redis，**无需预装环境**。
- 所有路径从脚本自身位置推导，整个文件夹可拷到任意盘符/机器，双击 `start-all.cmd` 即可运行。
- 数据库连接、存储路径、JWT 密钥等均支持环境变量覆盖。

### 8.4 可测试性

- 单元测试 **500 项**，全部纯逻辑（Mockito mock mapper，不连 MySQL/Redis）。
- `MapperSqlContractTest` 用 SQL 契约断言守护「带 project_id」「不含某些字段」等硬约束。
- 端到端验证脚本覆盖后端接口（`verify-p03-m4.ps1` 204 项）与前端渲染冒烟（`verify-p03-m4-ui.ps1` 63 项）。
